# Exact binary64 floating point

F64 is an admitted [GEN-1 generic argument](generic-functions.md).
`identity<f64>(x)` transports the exact ordinary binary64 value; generic branches,
loops and recursion use concrete f64 values after Core specialization. Signed
zero, subnormals, infinity and NaN payload transport retain the existing policy.
Concrete instances use F64/fp64-v6; a generic definition has no ABI profile.

An explicit [computed property](properties.md) may have type f64. Getter
`PTR → F64` and setter `PTR, F64 → void` use fp64-v6 and LLVM `double`.
Finite values, signed zero, subnormals, infinities and NaN payloads retain exact
binary64 transport. Accessors add no F32 conversion, fast-math or contraction.
F64 vectors remain unsupported.

`f64` is exactly IEEE-754 binary64: one sign bit, 11 exponent bits, 52 stored
fraction bits, 53-bit significand precision, exponent bias 1023. It is distinct
from f32 and every integer or other type. Neither C double nor the target defines
its meaning. `double`, `float64` and `real` are not aliases.

```astra
f64 add(f64 a, f64 b) { return a + b; }
f64 example() {
	f64 x = 9007199254740993.0;
	f32 narrow = x as f32;
	return (narrow as f64) + x;
}
```

Decimal tokens use the existing [F32 grammar](f32.md#literals): digits with a
fraction or decimal exponent. Signs are unary operators. [Precision suffixes](floating-literals.md)
select f32/f64 before rounding; explicit NaN/infinity spellings remain unsupported.
Without a suffix the expected type controls conversion directly: `f64 x=1.25;`
converts decimal to binary64, while `f32 x=1.25;` converts directly to binary32.
No decimal-to-f32-to-f64 intermediate exists for contextual f64 literals.
Uncontextualized decimals remain f32. `as` checks its operand without destination
context: `1.0000000000000002 as f64` widens the default f32 literal; to obtain the
direct binary64 value, write `1.0000000000000002d` or initialize an f64 binding
with the unsuffixed decimal. A suffix fixes its type despite context.

The compiler owns exact locale-independent decimal conversion using nearest,
ties to even, integer midpoint comparisons and a proven bounded digit buffer.
Host strtod/scanf/atof, host double and LLVM decimal parsing are not authorities.
`9007199254740993.0` (2^53+1) becomes bits `0x4340000000000000` (2^53).
`0.0` is `0x0000000000000000`; `-0.0` is `0x8000000000000000`.
Literal overflow is valid infinity; tiny literals round to subnormals or zero.

Same-type `+ - * /` return f64. Each operation rounds separately to binary64
under nearest/ties-even; `(a*b)+c` rounds twice. Reassociation, excess precision,
FMA contraction and all fast-math assumptions are forbidden. Unary minus toggles
the sign including zero; unary plus is identity. Remainder and bit operations
are unsupported. `f32 + f64`, integer/f64 arithmetic, implicit assignments and
mismatched arguments/returns reject. Decimal integer tokens do not become floats.

Both zeros, all subnormals, normal finite values, infinities and NaNs are supported.
Division by zero does not trap: `1.0/+0.0` yields positive infinity,
`1.0/-0.0` negative infinity and `0.0/0.0` NaN. Overflow produces infinity;
underflow rounds through the subnormal range to signed zero. FTZ/DAZ is not part
of Astra semantics. Loads/stores preserve exact values without arithmetic rounding.

`== != < <= > >=` require matching floating types and return scalar bool.
Either NaN makes all but `!=` false; `!=` is true even against another NaN.
The zeros compare equal but remain distinguishable by reciprocal sign. There is
no total order or payload inspection. As in F32-1, NaN payload, sign and
signaling/quiet construction are not stable source data. Arithmetic and
conversions may select quiet NaNs; no new payload guarantee is introduced.

`f32 as f64` is exact widening of every finite binary32 value.
`f64 as f32` is correctly rounded nearest/ties-even narrowing. The exact f64 tie
`1.000000059604644775390625` narrows to f32 `0x3f800000`. Narrowing overflow yields
signed infinity; underflow yields a normal, subnormal or signed zero. Both casts
preserve zero/infinity signs and the shared NaN doctrine.
[Scalar integer/float casts](numeric-conversions.md) are explicit; implicit
promotions remain unsupported. See [conversions](conversions.md).

F64 uses ordinary locals, branch joins, loop carries and native parameters/results.
Struct/class fields, methods and constructor parameters admit f64 under existing
scalar rules. Owned/borrowed Resource and object channels coexist with f64,
including an owned object result plus by-value f64 arguments. Ownership evaluation,
transfer commit and cleanup ordering do not change.

Storage parity includes `f64*`, `f64[N]` and `f64[]`. Direct and pointer accesses
remain coherent with aliasing, borrowing and null traps. Arrays use the existing
length/index rules; slices support full/subrange views and borrowed native
parameters. No f64-specific Place or memory architecture exists.

Native by-value f64 is F64 in [fp64-v6](../abi/native-fp64-v6.md). Body-only f64
does not upgrade a native profile. `f64*` remains PTR and borrowed `f64[]` remains
SLICE(PTR,I32), requiring only slice-v5 absent another by-value F64 channel.
LLVM realizes f64 as double with bit-exact constants and ordinary strict floating
operations. F32 remains float. CABI-FP-1 separately qualifies source extern(C),
export(C) and VAPI boundaries: f64 transports as exact C double under
[scalar-fp-v2](../abi/c-fp-v2.md), without conversion. VAPI `double` resolves to
f64 plus ForeignAbi.C; it creates no Astra source alias. Only qualified C
binary64 targets are admitted. Pure transport preserves signed zeros,
subnormals, infinities and quiet NaN payload bits; foreign arithmetic has no
payload-preservation promise. No double*, C aggregates or process arguments
are added.

Execution initially qualifies the established default x86-64 Linux environment:
nearest/ties-even, masked exceptions, preserved subnormals, empty CPU/features.
Foreign code must restore that environment; dynamic rounding changes and exception
flags are not Astra state. Unsupported targets remain unqualified. The language
makes no SH-4 hardware/software lowering choice.

F64 vectors, splats, lanes, DSP, dot/MAC,
FMA, transcendental functions and additional formats are deferred. See
[ADR 0054](../decisions/0054-exact-binary64.md) and
qualification.

## Explicit generic capabilities

f64 satisfies Eq, Ordered and Numeric. Generic instances preserve binary64
rounding, NaN and signed-zero comparisons, IEEE division by zero and separate
multiply/add rounding. Numeric does not impose integer trap semantics on f64.
Concrete f64 boundaries still select fp64-v6; there is no witness channel.
See [generic capabilities](generic-capabilities.md).
